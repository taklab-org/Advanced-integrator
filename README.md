# Advanced-integrator

MATLAB/INTLAB reproducibility code for three computer-assisted computations for
the two-dimensional Ohta–Kawasaki equation: global existence for `num5` and
`num7`, and a projected boundary-value problem (`pbvp`, Morse index 4 to 3).

**No computed datasets, MAT files, saved trajectories, checkpoints, INTLAB
distribution, or machine-specific INTLAB cache are distributed.** The fixed
Fourier coefficients in `initial_num5.m` and `initial_num7.m` define the initial
value problems; they are input specifications, not saved proof outputs.
PBVP eigenvectors, target approximation, candidate orbit and all validation
bounds are regenerated by the code.

## Requirements

- MATLAB R2024b or a compatible later release, with Parallel Computing Toolbox
  for the GE examples. PBVP runs serially.
- An independently installed, licensed INTLAB (tested with V13).
- Java support (MATLAB's usual JVM) for file identities and SHA-256.
- Working directed rounding and rigorous interval matrix multiplication in
  **every** computing process. The launcher checks scalar rounding, INTLAB's
  rounding self-test, and 512/2352 square matrix products before proof work.
  A failing runtime check stops the run; do not disable it.
- Sufficient memory. Choose the worker count for the machine; the default is
  two workers, two BLAS threads per worker, and two client BLAS threads.
  The historical 10-worker run used a 128 GiB machine. Do not copy that count
  onto a machine without a suitable memory budget.

There are no required symbolic, optimization, or external trajectory datasets.
INTLAB is deliberately external: this repository does not install it or alter
its numerical library. Use the appropriate BLAS/rounding configuration for the
host. In particular, a successful scalar test alone does not establish matrix
rounding correctness on Apple Accelerate.

## Run all three from a terminal

Python 3 is optional; this launcher uses its standard library only. Each
example runs in a fresh MATLAB process, in sequence:

```text
python reproduce.py --intlab-root /path/to/INTLAB --case all --output /absolute/new/output
```

Use `--matlab /path/to/matlab` when MATLAB is not on PATH. `--workers`,
`--threads`, and `--client-threads` configure resource counts. Use `--smoke`
for short GE kernel checks (the PBVP case still runs fully).

## Run a complete example

Start a **fresh MATLAB process for each example**. Point `INTLAB_ROOT` at the
directory containing `startintlab.m`, or pass that directory explicitly:

```matlab
cd('/path/to/Advanced-integrator')
run_case('num5', '/path/to/INTLAB', '/absolute/output/num5')
```

In separate fresh sessions:

```matlab
run_case('num7', '/path/to/INTLAB', '/absolute/output/num7', ...
    struct('Workers',4,'Threads',2,'ClientThreads',8))
run_case('pbvp', '/path/to/INTLAB', '/absolute/output/pbvp')
```

Use a **new, empty output directory** each time. If omitted, outputs go to the
ignored `outputs/<example>_<timestamp>/` directory. All candidates, Phase 2/3
datasets, checkpoints, logs and results are generated there. No saved result
is accepted as a replacement for running the proof.

For command-line runs, set `MATLABPATH` to the repository's `runtime` directory
before launching MATLAB. Its no-op `startup.m` prevents worker startup from
automatically calling full INTLAB initialization. Set `INTLAB_ROOT` in the
environment, then from the repository directory run, for example:

```text
matlab -batch "run_case('num7',getenv('INTLAB_ROOT'))"
```

The client initializes INTLAB serially. Each fresh process worker uses the
installation's `startintlab_minimum.m` if available, with prepared-cache checks.
For a standard installation without that local extension, full startup is
serialized across workers, avoiding concurrent cache writes. Do not run an
unrelated INTLAB initialization against the same cache during this setup.
This modifies only the installation's normal startup cache; it never ships or
imports a cache from another machine.

Each run records all distributed MATLAB source identities and checks that
they remain unchanged before writing success. Keep the release source tree
read-only while a calculation is running.

## What each run computes

| Example | Fourier truncation | Finite interval | Variational block | Middle phase | Terminal block |
|---|---|---|---|---|---|
| num5 | [20,20] | [0,13], 208 steps of 1/16 | [7,7] | direct terminal test, normally 0 steps | [20,20] |
| num7 | [28,28] | **[0,8], 128 steps of 1/16** | [7,7] | [12,12], maximum step 0.1 | [28,28] |
| pbvp | [12,12] | [0,0.1], normally four steps | [3,3] | projected boundary equations | not applicable |

Both GE cases use parameters `[0,1,0.39]`, domain factors `[1,1.1]` and
sequence weight `nu=1`. The num7 finite proof is generated **directly to t=8**
before the middle phase starts. It does not generate a proof to t=8.625 or
restrict/import a parent computation. The middle step count is determined by
the strict terminal test, not forced to a recorded value.

The GE numerical kernels are kept in separate source trees to preserve their
recorded versions. Do not add both trees to one MATLAB path. `run_case` selects
only one, along with the reviewed independent-column `chebmag` parallelization.
PBVP uses a separate source tree and a freshly generated Newton/ODE candidate.

## Success and reproducibility

A run is successful only if `SUCCESS`, `summary.json`, and `result.mat` are
written after the strict checks. A MATLAB exit with no result is not a proof.
Failures write `FAILED` and rethrow the error. GE requires all five validation
flags, valid source/data provenance, strict radii-polynomial negativity and
`Z<1`; the middle tests also require positive Schur complements and Neumann
bounds below one. PBVP checks all three componentwise radii inequalities and
`max(Z)<1`. GE additionally recomputes the algebraic middle/terminal tests from
the freshly generated local enclosures.

**Bitwise equality is not a reproducibility requirement.** BLAS versions,
parallel scheduling, eigenbases and arithmetic order can change rounding
bounds, radii and the accepted middle step count. Compare the configured PDE,
initial coefficients, truncations, endpoint time and strict mathematical
inequalities. Never replace those inequalities with closeness to reference
numbers, nor set a certificate flag to true merely to match a table.

Historical results and their provenance are summarized in
[docs/results.md](docs/results.md). The latest recorded num7 result used a
full-138 restriction at t=8; the public entry deliberately implements the
requested direct-128 proof. Consequently its radii and step count can differ
even on the original machine. See [docs/validation.md](docs/validation.md) for
which publication paths were actually exercised during packaging.

## Single-interval installation/kernel check

```matlab
run_case('num7','/path/to/INTLAB','/absolute/output/smoke', ...
    struct('Workers',2,'Smoke',true))
```

This regenerates **one real Phase 2 and Phase 3 interval** and audits it. It
does not prove the full example; `summary.json` explicitly says `smoke_only`.
The near-origin interval bounds can be slow even for one interval; this is
not a fixed-duration test. The packaging task did not complete this diagnostic
to the end; see the precise validation scope below.
For PBVP use the full entry point, which is much smaller than the GE runs.
Full GE runs can take many hours or days depending on CPU, memory and workers.

## Layout and attribution

- `run_case.m`: portable entry point and strict result gates.
- `cases/num5`, `cases/num7`, `cases/pbvp`: numerical kernels and problem inputs.
- `runtime`: per-process INTLAB checks and process pool initialization.
- `docs`: reference summaries, source identities and validation notes.
- `tests`: source-only packaging checks.

Original source comments, author credits and third-party notices are retained.
See [NOTICE.md](NOTICE.md). INTLAB must be cited and licensed separately.
